# 바이오헬스AI 해커톤 대비 강의 정리

> **용도**: 해커톤 산출물을 수정할 때 참고/컨텍스트로 쓰는 문서. 강의에서 대회 측이 설명·강조한 내용과 활용해야 할 도구를 정리했습니다.
> **제외한 차시**: 4차시(인공지능 기초 개념), 5차시(신경망·CNN·Transformer) — 노코드 도구를 쓰는 이번 해커톤에는 불필요. 그래서 2단원에는 2-3만 있습니다.
> 각 소제목의 **(N차시)** 는 원본 파일 `N차시.json`에 대응합니다.

## 요약: 대회가 지정한 활용 스택과 강조한 것

### 활용해야 할 것 (강의에서 지정한 조합)
| 단계 | 도구 | 비고 |
|---|---|---|
| 모델 제작 | **Teachable Machine** (이미지 프로젝트 / Standard Image Model) | MobileNet 전이학습. 코딩 없음 |
| 모델 서빙 | **TensorFlow.js** | 브라우저가 추론 엔진 → 서버·GPU 불필요 (→ 8-1) |
| 웹 개발 | **Claude Code** | 기존 파일을 조금씩 수정하는 방식 |
| 배포 | **Vercel** (무료 정적 호스팅) | GitHub Pages도 대안 |
| 데이터 | 공개 의료 데이터셋 (Kaggle / Grand Challenge / MedMNIST / Hugging Face) | 즉시 다운로드 가능한 것 |

- **문제 유형은 이미지 분류(classification)로 한정.** 분할(segmentation)·검출(detection)이 필요한 주제는 범위를 벗어남
- 데이터는 강의에서 쓴 3개(X-ray/피부/안저)가 아닌 **새로운 데이터셋**을 직접 선정

### 대회 측이 강조한 것 (평가 기준)
1. **완주 > 기능 수.** 작더라도 끝까지 동작하는 것이 최우선. **데모로 보여지지 않는 기능은 크게 감점**
2. **AI는 보조 도구.** 진단처럼 단정하는 표현 금지, 최종 판단은 사람 (Human in the Loop)
3. **한계를 정직하게 명시하면 가점.** 감추면 오히려 감점. 해결 가능/불가능 난이도까지 구분해 설명
4. **과장된 주장 금지.** 정확도 하나로 자랑하지 말고 놓침(민감도) 중심으로 근거 제시
5. **출처·라이선스·데이터 제한점**을 산출물에 표기

### 기존 파일에 반영할 체크리스트 (위 강조점을 UI로 구현하는 항목)
- [ ] 결과 문구를 **"○○ 클래스와 유사하게 분류됨 (유사도 %)"** 형태로 — "폐렴입니다" 같은 단정 금지
- [ ] **판단 보류 임계값**(기본 0.7) — confidence 미달 시 "판단 보류, 전문가 확인 필요" 표시
- [ ] 화면에 **데이터셋 출처·라이선스·클래스 구성** 표기
- [ ] **"교육용 프로토타입이며 실제 진단·치료에 사용 불가"** 안전 문구 고정 표시
- [ ] **한계 문장** 표기 (예: "다른 장비로 촬영한 영상에서는 검증되지 않음")
- [ ] 업로드 실패 대비 **fallback**(내장 샘플 이미지 자동 로드)
- [ ] **Vercel 배포**로 발표자 노트북 외 접속 가능하게

## 1. 의료 AI와 디지털 헬스케어 배경
### 1-1 오리엔테이션: 해커톤 개요 및 방향 (1차시)

- **강의 성격**: 2026년 초급 몰입형 의료 AI 해커톤 (강원대학교 AI 분야 첨단 사업 인재양성 부트캠프 사업단 협력)
- **최종 목표(해커톤 종착지)**: 이미지 분류 모델 + 웹 프로토타입을 결합한 **데모** 제공
  - 이미지 분류 모델: 전문 AI 프레임워크로 직접 코딩하지 않고 **Teachable Machine**(노코드/캐주얼 접근)으로 제작
  - 웹 프로토타입: 이미 상용화된 생성형 AI 도구를 활용 — 강의에서는 **Claude Code**를 사용해 웹 개발 보조를 받음 (참고로 ChatGPT 계열은 Codex 사용)
  - 데모 형태 예시: 사용자가 이미지를 업로드 → 모델이 사전에 정한 클래스와 얼마나 유사한지를 막대그래프 등으로 표시
- **대회 측이 원하는 서비스의 성격**: "실제로 의료 AI를 사용하는 것처럼 보이는" 체험형 데모. 완성도 있는 상용 제품이 아니라, 이미지 분류+웹 UI가 자연스럽게 연결된 프로토타입 수준

### 1-2 의료 AI 배경 지식: 규제·신뢰성 맥락 (1차시)

- **왜 지금 의료 AI인가**: ① 수요 폭증(고령화·만성질환 증가 대비 의사 수는 한정) ② 기술 도약(CNN → 2020년경 Transformer/LLM과 이미지 동시 이해) ③ 신뢰성 검증 축적(2017년경부터 학술적 검증 시도, 이후 제도권 진입)
- **의료 AI 실사용**: 국내 빅5 병원 포함 이미 임상 도입 중이나, **AI 단독 판독은 불가** — 전부 "의사 보조" 형태로만 사용
  - 4대 활용 분야: 진료 문서 자동화(EMR 연계), 영상 판독 보조(진단 속도 개선), 환자 모니터링(웨어러블 연계), 환자 상담/행정 보조
- **디지털 헬스케어 vs 의료 AI**: 의료 AI는 "진단 보조" 중심의 좁은 개념. 디지털 헬스케어는 EMR·PACS 영상·웨어러블·유전체 데이터 등 건강 데이터 전반을 디지털 자산화하고 활용하는 더 큰 개념(라이프사이클 관점)
- **국내외 규제 동향**:
  - 한국: 2017년 세계 최초 AI 의료기기 가이드라인 발표, 2025년 1월 생성형 AI 의료기기 가이드라인 공식화(비공식 적용은 2024년 12월부터)
  - 미국: 혁신·승인 속도 우선, 책임은 사후에 개별 기업 단위로 부과
  - EU: 사전에 AI 제품 위험 등급 부여(의료 AI는 대부분 **고위험군**), 변경 시마다 문서화·가이드라인 준수 의무
- **공통적으로 요구되는 3원칙** (서비스/데모 설계 시에도 반영할 감각):
  1. **인적 감독(Human in the Loop)**: AI는 반드시 보조 용도로만 작동, 최종 판단과 책임은 사람에게 있음. UI/제품 설계도 이를 "전적으로 신뢰하지 않게" 구성해야 함
  2. **투명성·설명 가능성**: AI가 블랙박스이므로 완전한 인과관계 설명은 불가하지만, 확률/근거를 최소한으로 제시해야 함
  3. **데이터 편향 관리 및 사후 모니터링**: 특정 인종·성별 등으로 결과가 갈리지 않는 대표성 있는 데이터, 배포 후 성능 지속 추적

### 1-3 의료 AI와 디지털 헬스케어 이해 (2차시)

- 의료영상 AI 문제 유형 중 이번 해커톤은 **분류(Classification)**를 사용 (클래스 소수일 때 가장 빠른 프로토타이핑 가능, 대신 병변 위치는 못 짚음)
- AI 단독/사람 단독보다 **AI+사람 협업 시 정확도가 가장 높다**는 것이 여러 사례의 공통 결론 → 서비스는 "판단을 보조"하는 형태로 설계

### 1-4 AI는 어디서 무너지나 (3차시)

- **지름길 학습(shortcut learning)**: 모델이 병변이 아니라 무관한 단서(촬영 기기 마크, 표기용 잉크 등)를 외워서 맞히는 경우가 많음 → 학습 데이터에 병변과 무관한 인공물이 섞이지 않았는지 점검 필요
- **외부 검증 필수**: 같은 출처 데이터로만 검증한 정확도는 믿을 수 없음, 학습에 안 쓴 데이터로 별도 검증 필요
- **데이터 불균형 위험**: 특정 집단(인종·성별 등) 데이터가 적으면 그 집단에서 위험하게 틀림 → 데이터 편향 여부 점검 필요
- **자동화 편향**: 사람이 AI를 과신해 틀린 답도 그대로 따라가는 문제 → 서비스는 "AI는 참고 의견"임을 UI로 계속 알려야 함 (대회 의도와 직결)

## 2. 데이터 다루기
### 2-3 데이터를 나눈다: 학습/테스트 분리와 데이터 누수 (6차시)

- 데이터는 **학습용(train)/테스트용(test)** 폴더로 완전히 분리해야 함. **Teachable Machine은 이 분리를 대신해주지 않으므로 직접 폴더를 나눠야 함** (실습 시 실수 포인트)
- **데이터 누수**: 같은 환자의 이미지가 train과 test에 동시에 들어가면 안 됨(환자 단위로 분리) → 안 지키면 겉보기 정확도(예: 95%)와 제대로 분리해 평가한 정확도(예: 70%)가 25%p 가까이 벌어짐
- 정확도(accuracy) 하나만 보면 안 됨 — 클래스 비율이 한쪽으로 쏠리면(예: 정상 95%) "다 정상"이라고만 해도 정확도 95%가 나옴
- 의료 AI는 **놓침(false negative: 아픈데 정상이라고 오판)을 오탐(false positive: 정상인데 환자라고 오판)보다 훨씬 더 중요하게 줄여야 함** → 민감도(재현율)를 먼저 확보하고 특이도는 그다음
- **Confidence(신뢰도) 수치의 함정**: 확률이 높다고 정답 보증이 아니며, 학습한 적 없는 엉뚱한 이미지에도 높은 confidence로 자신 있게 오답을 낼 수 있음
- **데모 문구 작성 지침(그대로 적용)**: "정상이니 안심하세요" 같은 단정적 표현 금지 → "학습 예제 기준 OO 클래스와 유사, confidence 98%. 전문가 판단이 추가로 필요합니다" 식으로 보수적으로 표현

## 3. 의료영상 데이터 이해
### 3-1 의료영상 데이터 이해 (7차시)

- 병원 원본은 DICOM 포맷(환자 이름·생년월일 등이 메타데이터에 함께 들어 있고 용량이 큼)이지만, **공개 데이터셋과 이번 실습은 전부 PNG/JPG(8비트)로 이미 변환되어 있어 바로 사용 가능**
- 모델 입력은 보통 224x224x3(정사각형, 컬러 3채널)으로 리사이즈됨 → **너무 작은 병변은 리사이즈 과정에서 사라질 수 있음**(문제로 다룰 병변 크기 고려 필요)
- 흑백(X-ray, 초음파) vs 컬러(피부, 안저) 구분 중요: **피부·안저 사진은 색 자체가 진단 정보이므로 흑백 변환 금지**

### 3-2 세 가지 의료영상, 성격이 다르다 (8차시)

- **X-ray**: 흑백, 구조적(변수 적음), 2클래스로 단순화하기 쉬움 → 난이도 최저, 처음 시도하기 좋음
- **피부 병변**: 컬러(색 자체가 진단 정보), 클래스 수 많아짐, 배경/조명 영향 → 편향 이슈를 직접 겪게 되는 단계
- **안저(당뇨망막병증)**: 등급 분류 문제라 인접 등급 간 경계가 모호 → 문제 정의 자체를 다시 고민해야 함
- **라벨 신뢰도가 곧 모델 성능**: 라벨을 어떻게 달았는지(전문가 1인 단독 / 여러 전문가 합의·다수결 / AI·판독문 자동추출)에 따라 신뢰도가 다름 — 특히 안저처럼 등급이 애매한 문제는 전문가 간에도 판정이 갈리는 경우(관찰자 간 불일치)가 흔함

### 3-3 데이터를 고르고, 받으면 먼저 센다 (9차시)

- **데이터셋 선택 기준 4가지**: 구하기 쉬운가(공개 데이터), 클래스를 2~3개로 단순화할 수 있는가, 데모가 안정적으로 돌 만큼 데이터 편차가 적은가, 내가 이 데이터의 편향을 정직하게 설명할 수 있는가
- **찾을 곳**: Kaggle, ISIC Archive(피부), NIH·Stanford 공개 데이터(Chest X-ray 등), 관련 논문에서 인용된 표준 데이터셋
- **라이선스 확인 필수**: 대부분 최근 공개 데이터셋은 "비상업적(academic) 용도만" 허용 → 해커톤 학습용은 문제없지만, 이후 실제 서비스로 배포하려면 라이선스 재확인 필요
- **데이터 받으면 가장 먼저 할 일 = 클래스별 이미지 개수 세기(EDA)**: 클래스 불균형 여부 확인(예: HAM10000 데이터셋은 최다 클래스와 최소 클래스가 50배 이상 차이) → 불균형 심하면 일부만 샘플링하거나 보정 필요
- 개인정보 비식별화는 공개 데이터셋이면 대부분 이미 처리되어 있음 (다만 공개된 지 얼마 안 된 최신 데이터셋은 미흡한 경우가 있어 한 번은 확인)
- **결과물에 반드시 남겨야 할 기록(데모/보고서에 명시)**: 데이터 출처·라이선스, 라벨링 방식, 클래스 수, 데이터 제한점, 그리고 **"교육용 프로토타입이며 실제 진단·치료에는 사용 불가"라는 안전 문구** — 해커톤 산출물에 꼭 포함해야 하는 부분

## 4. Teachable Machine과 모델 학습
### 4-1 Teachable Machine 이해 (10차시)

- **정체**: Google이 만든 코드 없는(no-code) 브라우저 기반 학습 도구(TensorFlow.js). 설치·결제 불필요, **데이터가 서버로 전송되지 않고 브라우저 안에서 전부 처리됨**
  - 단, **프로젝트 저장·불러오기와 모델 클라우드 업로드에는 Google 계정 로그인이 필요** → 해커톤 전에 로그인 상태를 미리 확인해 둘 것
- **내부 동작**: 경량 모델 **MobileNet(2018, Google)**에 전이 학습(transfer learning)만 적용 — 학습이 빠르고 쉬운 대신, **다른 모델로 바꿀 수 없어 성능 한계에 부딪히면 해결책이 제한적**
- 프로젝트 종류 3가지(이미지/오디오/포즈) 중 **이미지 프로젝트**를 사용 (Image Classification)
- **배포 방식 2가지**: ① 모델 다운로드해서 직접 서버에 올리기 ② **클라우드에 업로드해 API로 서빙** — 해커톤에서는 ②를 추천 (이후 Claude Code로 이 API를 호출하는 웹페이지를 만드는 흐름)

### 4-2 어떤 모델을, 왜 이렇게 배우나 (11차시)

- **전이 학습(transfer learning) 원리**: MobileNet의 특징 추출 레이어는 고정(freeze)하고, 맨 마지막 분류기(head)만 새로 학습 → 데이터·시간이 적게 들어 클래스당 수십~수백 장, 학습 수십 초~몇 분이면 충분 (권장: 클래스당 100~1,000장)
- **한계(중요)**: MobileNet은 일반 사진(개, 자동차, 꽃 등)으로 학습되어 선·모서리·색 같은 저수준 특징은 잘 잡지만, **의료영상의 미세한 도메인 특화 차이는 못 잡을 수 있음** → 결과가 그럴듯해 보여도 바로 신뢰하지 말고 검증 필요
- **실습 6단계**: 프로젝트 생성 → 클래스 이름 정하기(영어 권장, export된 모델에 그대로 노출됨) → 클래스별 이미지 업로드(클래스끼리 섞이지 않게) → Train → Preview로 확인 → Export(클라우드 서빙 또는 다운로드)
- 프로젝트 생성 시 **"Standard Image Model"** 선택 (Embedded 모델은 초소형 기기용이라 정확도보다 속도 우선 — 우리 목적과 다름)
- 학습은 브라우저 안에서 도니 **학습 중 탭 전환 금지**

### 4-3 학습 설정을 이해하고, 바꿔본다 (12차시)

- **조절 가능한 하이퍼파라미터 3개**: 에포크(반복 횟수) / 배치 사이즈(한 번에 학습할 이미지 묶음, 최대 512) / 러닝 레이트(피드백 보폭)
  - 에포크 너무 적음 = 덜 배움, 너무 많음 = **과적합**(학습 데이터는 잘 맞히지만 새 이미지는 오히려 틀림)
  - 배치 사이즈는 크게(최대값) 두는 게 보통 유리
  - 러닝 레이트가 가장 민감하고 실전에서 제일 많이 조정하게 되는 값(너무 작으면 수렴 느림/최적점 못 찾음, 너무 크면 학습 자체가 발산)
  - 튜닝 순서 추천: 배치·에포크 먼저 고정하고 마지막에 러닝 레이트를 조정
- **테스트는 반드시 학습에 안 쓴 이미지로**: 학습 완료 ≠ 좋은 모델. Preview에서 새 이미지를 넣어 직접 확인 필요
- **Confidence(막대 수치)의 의미 재확인**: "정답 확률"이 아니라 "학습한 클래스 중 어디에 더 가까운가"일 뿐 — **모델은 "모르겠다"를 말하지 못하고 엉뚱한 이미지(예: 고양이 사진)를 넣어도 억지로 학습된 클래스 중 하나로 답함** → 입력 이미지가 알맞은 종류인지는 사람이 걸러야 함
- **Export 결과물**: 공유 링크(클라우드 URL) 안에 model.json(모델 구조)·metadata.json(클래스명 등)·weight.bin(가중치) 3개 파일 존재 → 이 URL을 API처럼 호출해 웹페이지에서 예측 결과를 받아오는 구조

## 5. 모델 제작 실습Ⅰ: 폐질환(X-ray) 분류
### 5-1 모델 제작 실습Ⅰ (13차시)

- **사용 데이터셋**: Kaggle 공개 소아 흉부 X-ray(Kermany 등), 정상 1,583장 vs 폐렴 4,273장(train+val+test 합계 5,856장 JPEG. 이 중 train 폴더만 보면 정상 1,341 / 폐렴 3,875), CC BY 4.0(출처만 밝히면 교육·실습 사용 가능)
- **중요한 제한점**: 1~5세 소아 환자 + 단일 병원에서만 수집됨 → **성인이나 다른 병원 X-ray에는 성능이 떨어질 수 있음** (1-4의 "외부 검증 필요"·"지름길 학습"과 동일한 맥락)
- **모델이 봐야 할 실제 특징**: 정상은 양쪽 폐가 고르게 어둡고, 폐렴은 염증(침윤)으로 조직 밀도가 높아져 한쪽이 뿌옇게 밝아짐 — 이 차이를 모델이 진짜로 캐치하는지가 신뢰도의 핵심

### 5-2 모델을 만든다 (14차시)

- **Kaggle zip 압축 해제 시 주의**: 폴더 안에 동일 이름 폴더가 중첩된 경우가 많음(예: chest_xray/chest_xray) → 실제 학습에는 **train 폴더만 사용**, 기본 제공된 validation 폴더는 클래스당 8장뿐이라 신경 쓸 필요 없음
- Teachable Machine은 업로드한 이미지를 **내부적으로 자동 85:15로 나눠 15%를 자체 검증(validation)용으로 씀** (우리가 만드는 train/test 폴더 분리와는 별개)
- **고급 설정 > 하단의 정확도·손실 그래프로 과적합을 실제로 확인 가능**: train loss는 계속 내려가는데 test loss가 특정 지점부터 다시 올라가면 과적합 신호 (4-3에서 배운 개념의 실제 사례)

### 5-3 정직하게 평가한다 (15차시)

- **혼동 행렬(confusion matrix)에서 가장 주시할 칸은 false negative(폐렴을 정상으로 놓침)** — 정답률 하나만 보지 말고 이 칸을 최소화하는 방향으로 봐야 함 (오탐(false positive)은 추가검사로 이어져 상대적으로 덜 위험)
- **중요한 구분**: 병원별 장비·촬영법 차이로 인한 문제는 이후 파인튜닝/도메인 어댑테이션으로 어느 정도 보완 가능하지만, **소아 데이터로 학습해서 생기는 편향(성인과 골격 구조 자체가 다름)은 이런 기법으로 해결 안 됨** — 근본적 한계
- **실전 트러블슈팅**: 학습이 너무 느리면 이미지가 너무 많은 것 → 도구 동작을 확인하는 실습 목적이면 클래스당 50~100장이면 충분. 테스트가 "너무 완벽하게" 다 맞으면 오히려 의심(학습에 쓴 이미지를 실수로 다시 넣었는지 확인)
- **오답 리뷰 방법**: 학습에 안 쓴 이미지를 하나씩 Preview에 넣어 실제 라벨/예측/confidence를 직접 기록 — 가장 가치 있는 사례는 "애매하게(50%대로) 폐렴을 놓친 경우" (모델이 더 배우면 나아질 여지가 있는지 판단 근거가 됨)
- Export한 모델 URL·클래스별 성능·오답 사례 메모는 **버리지 말고 보관** → 이후 웹서비스 개발 단계(9단원)에서 그대로 재료로 사용

## 6. 모델 제작 실습Ⅱ: 피부병변 분류
### 6-1 모델 제작 실습Ⅱ (16차시)

- **피부 이미지가 X-ray보다 어려운 이유**: 컬러·조명·배경·피부톤 변수가 많아 정보량이 많은 만큼, 모델이 **병변이 아니라 배경·눈금자·잉크 표시·피부톤 같은 엉뚱한 단서에 기댈 위험이 X-ray보다 훨씬 큼**
- **사용 데이터셋**: HAM10000(Kaggle, ISIC 2018과 동일), 약 10,015장, 7개 클래스. **클래스 불균형 심함**(양성점 NV 혼자 2/3, 상위 3개 클래스가 90% 차지) → 실습 전략: 상위 2~3개 클래스만 골라 쓰는 게 유리(나머지 소수 클래스는 Teachable Machine에서 자동으로 무시되기 쉬움)
- **사람이 양성점 vs 흑색종(멜라노마)을 구분하는 기준 = ABCDE**: 비대칭(Asymmetry), 테두리 불규칙(Border), 색 여러 개 혼합(Color), 큰 지름(Diameter), 시간에 따른 변화(Evolution) — 모델이 이런 실제 병변 특징을 보고 있는지 검증할 때 참고 기준
- 이 실습의 목표는 "정확도"보다 **"어디서 왜 틀렸는지, 무엇을 넣었는지를 정직하게 설명할 수 있는가"**

### 6-2 데이터를 알고 들어간다 (17차시)

- HAM10000은 **폴더가 아니라 메타데이터 CSV의 `dx` 컬럼으로 클래스가 구분**되어 있어, 이미지를 클래스별로 넣으려면 CSV를 보고 직접 골라 업로드해야 함 (→ 10-2의 Claude Code 자동 정리 팁으로 해결 가능)
- 라벨 신뢰도 등급: `histo`(조직병리 검사로 확진, 골든 스탠다드에 가장 가까움) > `consensus`/`follow-up` 등 → 가능하면 **histo로 확진된 샘플 위주로 학습에 사용**하는 것이 좋음
- **실제 지름길 학습 사례**: 사진 주변에 촬영 프레임(테두리)이 크게 남은 이미지들이 특정 클래스(BKL)에 몰려 있었는데, 모델이 병변이 아니라 **"프레임이 큰지 여부"로 그 클래스를 판단하는 경향**을 보임 — 1-4에서 배운 shortcut learning의 실전 확인 사례
- Teachable Machine은 정사각형이 아닌 이미지를 넣으면 자동으로 가운데를 정사각형으로 크롭 후 224x224로 리사이즈함(별도 전처리 불필요하지만, 위 프레임 문제처럼 크롭 후에도 남는 요소는 주의)

### 6-3 모델은 어디서, 왜 틀리나 (18차시)

- **견고성(robustness) 판단 기준**: 조명·피부톤 등 병변과 무관한 요소가 바뀌었을 때 confidence가 조금 흔들리는 건(예: 85%→75%) 정상이지만, **다른 클래스로 뒤집힐 정도로 요동치면 모델이 병변이 아니라 주변 정보를 학습했다는 신호**
- **눈금자·잉크 표시가 지름길 단서가 되는 실제 메커니즘**: 의사는 "심각해 보이는" 병변 옆에만 mm 눈금자를 그려 넣는 경향이 있음 → 모델이 "눈금자가 있으면 위험한 병변"이라고 잘못 학습할 위험이 큼 (양성 점 클래스에는 눈금자가 거의 없기 때문)
- **인종·피부톤 편향**: 공개 데이터셋은 대부분 선진국 중심으로 수집되어 밝은 피부톤 위주 → 어두운 피부톤 환자에게는 성능이 크게 떨어질 수 있음. 이런 편향은 현재 인종차별의 일종으로 규정되어 **소송 등 법적 문제로 이어질 수 있음**(AI 윤리·법적 리스크)
- **Teachable Machine은 블랙박스라 내부를 못 열어보므로, 검증은 정성적 비교로 해야 함**: 같은 병변인데 주변 인공물(눈금자·잉크·배경)만 다른 이미지를 직접 넣어보며 예측이 크게 바뀌는지 확인하는 것이 사실상 유일한 검증 수단
- 실험할 때마다 **"원인 추정 → 검증 방법 → 결과"를 기록하는 습관**이 이후 개선 반복(iteration)에 중요 — 해커톤 진행 시에도 이 사이클을 유지할 것

## 7. 모델 제작 실습Ⅲ: 당뇨망막병증(안저) 판별
### 7-1 모델 제작 실습Ⅲ (19차시)

- **이번 데이터가 X-ray·피부보다 더 어려운 이유**: 라벨이 0~4단계의 **순서형(ordinal) 등급**이라 등급 경계가 모호함(전문의도 인접 등급끼리는 판정이 갈림) → 해커톤에서는 이를 **2클래스로 단순화**해서 접근하는 문제 재정의 전략을 사용
- **리사이즈로 인한 초기 신호 손실(중요)**: 조기 진단 신호인 미세혈관류는 원본에서 약 10픽셀 정도인데, 표준 입력 크기 224x224로 축소되면 1픽셀 수준으로 뭉개져 사라짐 → 3-1에서 배운 "작은 병변은 리사이즈로 소실될 수 있다"의 구체적 사례
- **데이터 품질 필터링 기준(안저 특화)**: 초점 흐림·너무 어두운 이미지는 학습 초반엔 제외하는 게 좋고, 시신경 유두·황반이 화면에 다 들어온 이미지 위주로 사용

### 7-2 당뇨망막병증 등급과 병변 (20차시)

- **사용 데이터셋**: APTOS 2019(Kaggle), train 3,662장, ICDR 0~4단계 라벨(CSV 기반), 단일 병원·현장 촬영이라 화질 편차 있음
- **5등급을 그대로 학습하기 어려운 이유**: 인접 등급 경계가 애매함 + 조기 병변(미세혈관류)이 리사이즈 과정에서 소실됨 + 클래스 불균형 심함(정상만 찍어도 정확도 49%)
- **문제 재정의 전략(그대로 적용 가능한 템플릿)**: 5등급 → 2클래스로 병합. **0+1단계 = "No DR", 2+3+4단계 = "Suspected DR"**
  - 주의점: 1단계를 "No DR" 쪽에 합친 이유는, 1단계의 미세한 신호가 리사이즈로 소실/혼동되기 쉬워 "Suspected" 쪽에 넣으면 애매한 라벨이 섞이기 때문
- **불균형 처리는 언더샘플링**: 병합 후 두 클래스 중 적은 쪽 숫자에 맞춰 많은 쪽에서도 동일한 수만 뽑아 학습(추가 기법 없이도 균형 맞춤)

### 7-3 당뇨망막병증 실습 (21차시)

- **CSV 라벨 데이터를 폴더처럼 다루는 실전 팁**: 스프레드시트(엑셀·한셀)에서 진단 라벨 컬럼에 자동 필터를 걸어 0/1, 2/3/4로 걸러낸 뒤, 해당 ID의 이미지 파일만 복사해서 Teachable Machine 클래스 상자에 드래그 앤 드롭 (→ 더 편한 방법은 10-2의 Claude Code 자동 정리)
- **민감도(Sensitivity/Recall) = TP/(TP+FN)**: 실제 환자를 얼마나 잘 잡아내는가, 의료 AI에서 가장 중요하게 높여야 하는 값
- **특이도(Specificity) = TN/(TN+FP)**: 실제 정상을 얼마나 잘 걸러내는가
- **트레이드오프**: 민감도를 높이면 애매한 경계 케이스까지 "양성"으로 포함시키게 되어 특이도는 자연히 낮아짐 — 이 둘은 항상 같이 움직이므로 정확도 하나만이 아니라 이 두 지표를 함께 보고해야 함

## 8. 모델을 웹서비스로 연결하기
### 8-1 TensorFlow 및 AI 모델 활용 (22차시)

**해결할 문제**: 학습한 모델이 Teachable Machine 사이트 안에만 존재해 남에게 보여줄 수 없음 → 내 웹페이지에서 불러와 쓰는 것이 목표.

#### TensorFlow란 무엇인가
- **Google이 만든 딥러닝 프레임워크.** PyTorch와 함께 AI 모델을 만드는 양대 도구이고, 이미지·음성·언어 모델을 다 여기서 구현할 수 있음
- **PyTorch vs TensorFlow**: PyTorch는 학습 중간 상태를 자유롭게 들여다보고 수정하기 쉬워 **연구자**들이 선호. TensorFlow는 **서빙(실제 배포)·엣지 디바이스(모바일·브라우저)** 쪽에 초점 → 그래서 Teachable Machine도 TensorFlow 계열
- **우리 범위에서 "TensorFlow를 쓴다"는 뜻**: 파이썬으로 신경망을 직접 코딩하는 게 아니라, **이미 학습된 모델 파일(model.json + weights)을 웹에서 불러와 쓴다**는 의미. 역전파·손실함수 같은 내부는 프레임워크가 알아서 처리하므로 몰라도 됨

#### TensorFlow.js — 브라우저가 곧 추론 엔진
- `.js` = JavaScript. **TensorFlow의 JavaScript 판**이고, 웹페이지 안에서 딥러닝 모델을 직접 실행시켜 줌
- 웹 구성 요소 관계: **HTML**(화면 구조) / **CSS**(디자인) / **JavaScript**(동작·로직) → **모델 로딩과 예측은 JavaScript 영역**
- **원래 방식**: 사용자가 이미지 업로드 → 회사 서버의 GPU로 전송 → 서버에서 추론 → 결과를 돌려받음 (GPU 서버 비용·구축 필요)
- **TensorFlow.js 방식**: 모델 파일을 브라우저가 한 번 내려받아 **사용자 기기에서 바로 추론**
  - 장점: **GPU 서버 불필요**, 이미지가 외부로 전송되지 않아 **개인정보 측면에서 유리**, 통신 지연 없음
  - 트레이드오프: 모델 파일이 사용자에게 노출됨 → 상용 서비스라면 위험하지만 **해커톤·교육용에는 문제없음**
- **설치 불필요**: 필요한 라이브러리 2개를 CDN으로 불러오면 끝 (별도 개발 환경 구축 없음)
  ```html
  <script src="https://cdn.jsdelivr.net/npm/@tensorflow/tfjs@latest/dist/tf.min.js"></script>
  <script src="https://cdn.jsdelivr.net/npm/@teachablemachine/image@latest/dist/teachablemachine-image.min.js"></script>
  ```
  - `tfjs` = 연산 엔진, `teachablemachine-image`(`tmImage`) = Teachable Machine 모델 전용 로더

#### Teachable Machine이 내주는 3개 파일
Export → 클라우드 업로드하면 공유 URL이 나오고, 그 URL 안에 3개 파일이 있음:

| 파일 | 내용 |
|---|---|
| `model.json` | 모델 구조(아키텍처) — 고정(freeze)된 MobileNet + 우리가 붙인 분류기(head) |
| `metadata.json` | 클래스 이름 목록, 입력 이미지 크기, TensorFlow.js 버전 등 |
| `weight.bin` | 학습으로 정해진 가중치 숫자 뭉치 (직접 열거나 고칠 필요 없음) |

- **이 정보들이 사전 정의되어 있어야 TensorFlow.js가 모델을 복원할 수 있음.** Teachable Machine이 그 형식으로 미리 만들어 제공하는 것
- **URL 정상 작동 확인법**: 브라우저 새 탭에서 `<모델URL>model.json`, `<모델URL>metadata.json`을 열어 텍스트가 보이면 정상 호스팅 중 (모델 URL은 끝에 `/`가 붙어 있으므로 그 뒤에 파일명만 붙임)
- 모델을 재학습했으면 **다시 업로드**해야 URL 내용이 갱신됨. 인터넷 연결 필요

#### 실제 코드는 3줄
```js
const URL   = modelUrlInput.value.trim();                 // 끝에 / 포함된 모델 URL
const model = await tmImage.load(URL + "model.json", URL + "metadata.json");
const pred  = await model.predict(imgElement);            // [{className, probability}, ...]
```
- `predict`는 **클래스별 확률 배열**을 돌려줌(합계 100%). 가장 높은 항목이 Top class
- **입력 전처리는 `tmImage`가 자동 처리**: 짧은 변을 224로 맞추고 가운데를 정사각형으로 크롭 → 224×224로 리사이즈, 픽셀값 정규화까지
  - 학습 때와 추론 때 전처리가 같아야 결과가 맞는데, Teachable Machine 계열은 이게 자동으로 일치됨
  - 반대로 **전처리를 커스터마이즈할 수 없다는 게 이 방식의 한계** (작은 병변 소실 문제 → 3-1, 7-1 참고)

#### 자주 나는 오류
- **모델 로드 실패**: URL 오타/공백/`model.json` 경로 누락 → 위 확인법으로 점검
- **CORS 차단**: 모델을 파일로 다운로드해서 쓰거나 로컬·호스팅 환경이 섞일 때 발생 가능. 클라우드 URL 방식이면 거의 안 생김
- **미지원 형식**: DICOM은 안 됨 → JPG·PNG로 변환해서 업로드

### 8-2 웹페이지는 어떻게 여나 (23차시)

- 제공된 템플릿 HTML 파일을 **더블 클릭해서 브라우저로 열기만 하면 됨** (설치·편집기·로컬 서버 전부 불필요) → 모델 URL 입력 → 이미지 업로드 → 결과 확인
- **판단 보류(threshold) 기능이 커스터마이징의 핵심 예시**: confidence가 기준치(예: 70%) 미달이면 단정하지 않고 "판단 보류"로 표시하도록 코드에 구현 가능 — 앞서 배운 "AI는 참고 의견" 원칙을 UI로 실현하는 방법
- **한계**: 더블 클릭으로 열면 주소가 `file://`이라 **내 컴퓨터에서만 열림 → 다른 사람에게 링크 공유 불가**. 외부 공개하려면 서버 호스팅이 필요하고, 이는 9단원(Claude Code)에서 다룸

### 8-3 모델을 웹에 잇기 (24차시)

- **템플릿 동작 흐름**: 모델 URL 입력 → TensorFlow.js가 model.json·metadata.json·weight.bin을 브라우저에 캐싱 → 이미지 업로드 시 자동 전처리(짧은 변을 224로 맞추고 중앙 크롭) → 클래스명 + 유사도 반환
  - 핵심 코드는 3줄뿐: URL 읽기 → `tmImage.load(model.json, metadata.json)` → `model.predict(image)`
- **판단 보류 임계값(hold threshold) 조정 = 가장 중요한 커스터마이징 포인트**
  - 기본값 0.7 → 이보다 낮은 confidence면 "판단 보류, 사람이 직접 확인" 안내
  - **임계값을 낮추면** 확실하지 않은 정상 케이스까지 환자 쪽으로 넘기게 됨(재현율 우선 = 의료용에 적합), **높이면** 확실할 때만 특정 클래스로 판정
  - Teachable Machine 기본은 그냥 반반(1등 클래스 선택) → 정확도 중심. 의료에서는 재현율 중심으로 바꿔야 함
- **결과 표기 원칙**: "폐렴입니다"가 아니라 **"○○ 클래스와 유사하게 분류됨 (유사도 %)"**로 표현하고, 학습 데이터 정보와 비보증 안전문구를 함께 표시
- **자주 나는 오류**: 모델 로드 실패(URL 오타/공백 → model.json이 열리는지 확인), DICOM 등 미지원 형식(JPG·PNG로 변환), 라벨 이름 이상(Teachable Machine에서 클래스명을 잘못 입력한 경우)

## 9. Claude Code 활용 의료 AI 웹서비스 개발
### 9-1 개발 환경 준비와 Claude Code 이해 (25차시)

- **접근 방식**: 백지에서 새로 만들지 않고 **8단원에서 만든 동작하는 템플릿을 조금씩 수정**하는 방향 (뭐가 되고 안 되는지 구분이 쉬워짐)
- **채팅형 AI vs 에이전틱 AI**: 채팅형(ChatGPT·Claude 웹)은 질문에 답만 주고 복붙은 사람이 함. 에이전틱(Claude Code·Codex)은 **파일을 직접 읽고 수정하고 실행해보고, 에러가 나면 스스로 고쳐 재시도**함
- **Claude Code 작업 사이클**: 사람이 자연어로 요청 → 코드 읽고 계획 수립 → (허락 요청) → 파일 수정 → 실행·결과 확인 → 사람이 직접 확인 → 필요하면 반복
  - 어디를 고칠지 사람이 짚어줄 필요 없음(폴더 전체 맥락을 스스로 파악). 단, 파일 수정·실행 전에 허락을 묻는 단계가 있어 위험한 작업을 막을 수 있음
- **설치할 것 2가지**: ① **VS Code**(무료 편집기, 로그인 불필요) ② **Claude 앱**(터미널이 익숙하지 않으면 앱 방식 권장)
- 준비 절차: VS Code 설치 → 작업용 폴더 생성 → 그 안에 8단원 웹 템플릿 파일 넣기 → VS Code에서 해당 폴더 열기
- **이번 단원의 수정 목표 예시**: 데이터셋 제목·설명 추가, 출처와 결과가 함께 보이는 카드 구성, 오류 시 자동 복구

### 9-2 토큰 관리와 수정 요청 원칙 (26차시)

- **토큰 한도가 해커톤의 실질적 제약**: 토큰은 5시간 세션·주간 단위로 한도가 있고 대화가 길어질수록 계속 쌓임 → 해커톤 하루는 5시간 세션 2번 정도로 계산해서 **토큰 사용 계획을 미리 세워야 함**
  - 절약법: 요청을 작게 나누기, 필요 없어진 대화는 `/clear`로 정리, 반복 지시는 CLAUDE.md에 정리(영어로 쓰면 토큰 절약)
- **권한(승인) 모드 선택**: 초반에는 **수동**(변경마다 확인)으로 감을 익히고, 익숙해지면 **계획 모드 + 자동**을 조합 (계획서를 먼저 받아 검토 후 승인하면 이후는 자동 진행). **권한 건너뛰기는 파일이 삭제될 위험이 있어 비권장**
- **수정 요청 3원칙 (해커톤에서 그대로 적용)**:
  1. **처음부터 전부 만들지 말 것** — "멋진 웹사이트 만들어줘" 같은 모호한 요청은 AI가 추측으로 메꿔 엉뚱한 결과가 나옴. 이미 동작하는 템플릿에서 조금씩 수정
  2. **건드리면 안 되는 영역을 명시할 것** — 특히 모델 로딩·예측 코드는 깨지면 화면 전체가 안 돌아감. "○○는 건드리지 마"를 요청에 포함
  3. **한 번에 한두 개만 바꾸고 눈으로 확인할 것** — 문제가 생겼을 때 어느 요청이 원인인지 특정할 수 있음
- 요청 시 `@파일명`으로 대상 파일을 명시할 수 있고, Claude가 브라우저를 띄워 결과를 스스로 확인하기도 함

### 9-3 좋은 프롬프트 설계와 Vercel 배포 (27차시)

- **좋은 요청의 3요소**: ① 범위(무엇을 바꿀지) ② 유지(무엇을 건드리지 말지) ③ 확인(무엇을 성공으로 볼지)
  - 나쁜 예: "결과 화면 예쁘게 해줘"
  - 좋은 예: "결과 카드에서 클래스명은 크게, confidence는 바와 숫자를 함께 보여줘. **예측 코드는 그대로 두고**, 업로드가 되는지 확인해줘"
- **배포는 Vercel(무료 정적 호스팅)로 Claude Code에게 요청 가능**: Vercel 가입·로그인 후 "이 서비스를 Vercel로 배포해줘"라고 요청하면 CLI 실행부터 배포·검증까지 처리. GitHub Pages도 대안
  - **배포 시에는 모델 URL을 매번 입력하는 방식보다, 모델 파일을 함께 배포하는 방식이 안정적**
- **처음부터 새로 만들 때 필요한 입력 정보**: 모델 URL + 배포 방식(Vercel) + 사용한 데이터셋 링크 → "서빙 페이지 작성 계획을 세워서 보여줘"로 계획 먼저 받기
- **유용한 명령어**: `/clear`(세션 초기화 = 토큰 절약 + 맥락 혼동 방지, 기능 단위로 새 세션 권장), `/rewind`(수정 전 시점으로 되돌리기), `/init`(CLAUDE.md 생성 — Claude에게 주는 프로젝트 사용설명서, 작업 이력이 쌓인 뒤 만드는 게 좋음)
- **해커톤 데모 안정화 체크리스트(중요)**:
  - 동작할 때마다 **화면 캡처·녹화로 남겨두기** (팀원이 코드를 수정해 충돌나면 데모가 깨질 수 있음)
  - 잘 되는 버전은 별도 백업 파일로 저장
  - 테스트 이미지를 프로토타입과 같은 폴더에 준비
  - 되돌리기가 가능하므로 겁내지 말고 시도할 것 (한 번에 하나씩 바꾸면 되돌리기도 깔끔)

## 10. 해커톤 준비
### 10-1 데이터셋 탐색 및 해커톤 준비 (28차시)

#### 대회 진행 방식과 시간 배분 (★가장 중요)
- **7월 말, 이틀에 걸쳐 진행(밤샘 세션은 없음), 총 약 17시간**. 이 중 앞부분(데이터셋 선정·팀 구성·논의)과 뒷부분(발표·데모 3~4시간)을 빼면 **실제 작업 시간은 10시간 미만**
- 그 10시간 안에서 리허설 1시간 + 안정화·자료정리 2~3시간 + 예비 버퍼 1~2시간을 빼면, **순수 개발·모델 학습에 쓸 수 있는 시간은 약 4~6시간** → 핵심 흐름은 사실상 첫날 안에 다 만들어야 함
- **데이터셋은 강의에서 쓴 3개(X-ray/피부/안저)가 아닌 새로운 것을 직접 찾아야 함**

#### 대회 측 평가 의도 (강사가 직접 언급 — 반드시 반영)
- **"완주"가 최우선 평가 기준**: 기능 욕심으로 미완성하는 것보다 작더라도 끝까지 동작하는 것이 훨씬 높게 평가됨
- **데모로 보여지지 않는 기능(머릿속에만 있는 기획)은 확실하게 크게 감점**
- 실제 해커톤에서 20~40% 팀이 기획한 것을 완성하지 못함 → 원인은 역량 과대평가, 기능을 페이지 단위로 나누지 않고 한 번에 완성하려는 시도
- **→ 전략: 끝까지 동작하는 작은 것부터 만들고 키워나가기. 기능은 무조건 작게 잡기**

#### 공개 의료 데이터셋 찾을 곳 (강사 추천 순)
- **추천**: Kaggle, **Grand Challenge**(MICCAI 의료 컨퍼런스의 경진대회·벤치마크 모음), **MedMNIST**, **Hugging Face Datasets**(분류·필터링이 잘 되어 있음)
- 피부 병변 특화: ISIC Archive
- **비추천**: TCIA(다운로드·전처리 난이도 높음), Google Dataset Search(검색 품질이 아쉬움), PhysioNet MIMIC(별도 교육 이수 자격 필요 — 짧은 해커톤에 부적합)

#### 데이터셋 선정 체크리스트
1. **라이선스**: CC BY(출처 표기), CC BY-NC(비상업), 대회 전용(재배포 제한) — 해커톤 기간 사용 + 재배포 없음이면 대부분 가능
2. **접근 조건**: **가입만 하면 즉시 다운로드 가능한지가 핵심** (승인 대기·교육 이수가 필요한 데이터셋은 시간 부족으로 부적합)
3. **출처**: 어느 병원에서 어떤 과정으로 수집했는지
4. **클래스 균형**과 **대표성**(장비·인구 구성이 통일되어 있는지)
5. **크기**: **클래스당 최소 수백 장 이상** 확보되어야 함
   - 참고로 장수 기준이 상황마다 다름: 도구 동작만 확인하는 실습은 클래스당 50~100장으로도 되고(5-3), 제출용 모델은 클래스당 100~1,000장 수준이 안정적(4-2)
- **최종 판단 기준 2가지**: ① 이미지 분류(classification)로 풀리는 문제인가 ② 클래스당 장수가 충분한가 → 정확도보다 "짧은 시간에 완주 가능한가"를 보는 기준

### 10-2 팀 구성과 1페이지 기획서 (29차시)

- **CSV 라벨을 폴더로 자동 정리하는 실전 팁(강사 시연)**: Claude Code에게 *"train.csv를 읽고 train_images 폴더의 이미지들을 0~4 클래스별 폴더로 정리해줘"* 라고 요청하면 코드를 짜서 즉시 처리해줌 → **Teachable Machine에 폴더째로 드래그 앤 드롭 가능** (6-2·7-3의 수동 필터링 노가다를 대체하는 가장 실용적인 팁)
- **팀 구성: 3~4인**, 역할은 ① 코드에 익숙한 사람 ② 의료 도메인 지식이 있는 사람(데이터셋 이해·공유) ③ 발표·정리에 강한 사람
  - 역할 분담: **데이터 / 모델 / 웹 / 설명** 4가지. 모델(Teachable Machine)은 손댈 게 거의 없으니 웹·데이터 담당이 나눠 맡고, 설명 담당이 문제·데이터·결과·한계 정리와 팀 리딩을 맡는 구조
  - 해커톤 시작 전에 본인 강점을 미리 정리해두면 팀 구성 시간이 단축됨
- **좋은 주제 vs 나쁜 주제**
  - 좋은 주제: 짧은 시간에 끝까지 만들 수 있음, 내가 익숙한 분야, 양질의 공개 데이터셋 존재, 한계를 구체적으로 말할 수 있음
  - 나쁜 주제: 임상 진단을 주장함, 쓸 데이터를 못 구함, **이미지 분류 범위를 벗어남(분할·검출이 필요)**, 결과를 신뢰하기 어려움
  - 해커톤 시간 안에 완벽한 제품이 나온다면 그건 이미 누구나 할 수 있는 것 → **한계를 구체적으로 인정·설명하는 것이 오히려 평가에 유리**
- **1페이지 기획서에 담을 7가지** (양식은 강사가 배포 예정. 제출 서류이자 팀 내 분쟁 방지 도구):
  1. 문제 정의 — 누구의 어떤 불편인가
  2. 사용자 상황 — 어떤 상황에서 사용하는가
  3. 데이터셋 — 어떤 공개 데이터셋, 어떤 클래스 (여러 데이터셋을 섞어 쓰는 것도 가능)
  4. 모델 — Teachable Machine 전이학습(전 팀 공통이지만 어떤 모델·기법인지 설명 가능해야 함)
  5. 웹 기능 — 기본은 이미지 업로드 → Top class 유사도 표시, 추가 기능이 있으면 명시
  6. 예상 데모 — 실제로 무엇을 보여줄지
  7. 한계 — 구체적으로 작성
  - **MVP(최소 구현 기능) 기준으로 작성**하고, 작업 중 수시로 이 기획서를 확인해 범위를 벗어나지 않는지 점검

### 10-3 병렬 작업 전략, 발표, 실패 요인 (30차시)

#### 모델이 나오기 전 병렬 작업 (병목 해소)
- 모델 URL은 순수 개발 구간(약 4~6시간) 중 **중반에야 나옴** → 그때까지 다른 팀원이 손 놓고 있으면 절반의 시간이 낭비됨
- **의존성 없는 일부터 먼저**:
  - 데이터 담당: 클래스 확정, 불량 데이터 제거·검수, 데이터셋 카드 작성
  - 웹 담당: 템플릿으로 UI 뼈대 잡기, **가짜 결과·샘플 이미지로 먼저 테스트**
  - 발표 담당: 문제 정의 재점검, 결과 슬라이드만 비워두고 나머지 자료 미리 채우기
- 모델 URL 나온 뒤: 실제 URL 연결 → 비워둔 슬라이드 채우기 → 리허설·백업 → 시간 남으면 추가 기능(리허설 팀 / 개발 팀 투 트랙)
- **스탠드업**: 일정 간격으로 짧게 모여 각자 진행 상황 공유 → **막힌 사람을 빨리 발견하는 것이 목적**

#### 발표 구성 (기획서 7항목을 풀어서 설명)
문제 → 데이터 → 모델 → **웹 동작 화면·라이브 데모(가장 중요, 시간 많이 배분)** → 잘 맞은 예와 confidence → 한계 → 개선점(MVP 이후 하려던 것과 시간 부족으로 못한 것)
- 발표는 "우리 이런 걸 만들었다"고 **자랑하는 자리** → 배경을 길게 떠들기보다 데모와 결과를 적극적으로 보여줄 것
- 진단처럼 단정하는 표현(문구·디테일 포함)은 지양

#### "정직한 한계"가 신뢰를 만든다 (★평가 포인트)
- 한계가 없는 모델은 없음. **한계가 없다고 하면 문제가 되고, 한계를 말하면 신뢰를 얻음**
- 한계를 감추지 말고 오픈하되, **해결이 불가능한 것인지 / 다음 기능으로 바로 해결 가능한 것인지 난이도를 구분해서 설명**하면 평가에 훨씬 유리
- 좋은 한계 문장 예: "다른 장비로 촬영한 영상에서는 검증되지 않아 리스크가 있음", "배경 표식에 반응할 수 있는 데이터셋군임"
- 한계를 말할 수 있다는 것 = 모델이 언제·어디서 틀리는지, Teachable Machine의 리사이즈 한계 등을 정확히 알고 있다는 증거 → **플랫폼 자체의 한계는 평가에서 참작됨**

#### 프로젝트 실패 3대 요인
1. **작동 안 하는 데모** — 백업 녹화가 있어도 감점
2. **과욕** — 다 하려다 아무것도 안 됨
3. **과장된 주장** — 자기 모델 성능을 정확히 측정하지 못한다는 뜻으로 받아들여짐 → 근거와 적절한 지표 제시 필요

#### 실전 팁
- **중간 점검 기준**: 절반 시간이 지났는데 웹에서 결과가 **한 번도 떠본 적이 없다면 위험 신호** → 기능 추가보다 최소 동작 확보를 항상 우선
- **Fallback 구현 요청**: "이미지 업로드가 실패하면 내장 샘플 이미지가 자동으로 올라가게" 같은 대비 로직을 Claude에게 짜달라고 요청
- **데모는 Vercel에 배포**해서 발표자 노트북 외에 현장의 다른 사람도 접속할 수 있게 할 것
- 발표 중 말문이 막힐 때를 대비해 **키워드 메모를 준비**하고, 막히면 팀원에게 아이컨택으로 넘길 것. **리허설을 하면 대부분 예방됨**
- 이틀차에는 강사가 현장을 돌며 상황을 봐줄 예정 → 막히는 부분은 그때 질문할 것
- **사전 준비 권장**: 해커톤 전에 Kaggle·Hugging Face·Grand Challenge를 둘러보며 **관심 데이터셋 3개 정도를 미리 골라두기**, AI 에이전트를 많이 써보며 계획·시뮬레이션 해두기 (사용량 편차가 결과 격차로 이어짐)
